# Second-machine bootstrap — issues & gaps

Context: setting up blackbox on a fresh macOS machine (darwin) where the daemon
was already built/installed/running on prod `:7264`. Walked the README
"Quick start" steps 3–6 (steps 1–2 pre-done). Date: 2026-05-29.

Connected via `http://127.0.0.1:7264/mcp?surface=ops`.

Ordered roughly by severity.

---

## HIGH — `bbox_absorb` is a no-op but the README still sells it as the reverse sync path

- **Live tool description**: "Compatibility no-op for the old rendered-file import
  path. Use bbox_bootstrap to import hand-authored instruction files, then render
  unidirectionally from the knowledge store."
- **README still says** (Knowledge lifecycle table + step 6): `bbox_absorb`
  "Detect external edits to rendered files and import them as unverified entries",
  and "`bbox_absorb` is the inverse — handy after you've edited a CLAUDE.md
  directly and want the change captured before a later render overwrites it."
- **Impact**: Step 6's entire migration loop ("Absorb any hand-authored content
  you want to keep") is built on a tool that no longer does anything. A user
  following the README to migrate global content will silently import nothing,
  then prune their originals, then render — and lose the content. The model is
  now unidirectional (bootstrap → store → render); the README still describes a
  bidirectional model.
- **Fix**: Rewrite the Knowledge lifecycle section + step 6 to drop `bbox_absorb`
  as an import path. Either remove it from the table or clearly mark it
  deprecated/no-op. Re-explain "I edited a rendered file directly" recovery in
  terms of the new unidirectional flow.

## HIGH — fresh-machine trap: bootstrap declines an already-managed repo, but project render from the empty-for-that-project store clobbers committed content

This is the core footgun and it has no safe documented path.

- The repo's committed `CLAUDE.md`/`AGENTS.md`/`GEMINI.md` (74 lines: RX-V1/V2/V3,
  provider catalog, render hygiene, etc.) were rendered on the *original* machine
  and committed to git. They carry no `bb:managed` markers (project-scope files
  are wholly generated, so they use only the `<!-- Generated by blackbox -->`
  header, not markers).
- On the new machine the knowledge store has **no project-scope entries** for this
  repo (project wasn't registered until setup).
- `bbox_bootstrap` **refuses**: "All instruction files are already
  blackbox-generated. Nothing to bootstrap." — it detects them as generated and
  won't re-import.
- `bbox_render scope=project` (dry-run) would write a **6-line stub**
  (`@PROJECT.md` + header), i.e. it would **delete the 74 committed convention
  lines** in the working tree.
- Net: the committed conventions can be neither re-imported (bootstrap declines)
  nor reproduced (render stubs them). There is no supported second-machine path
  to reconcile "files are managed" with "local store is empty for this project."
  `bbox_absorb` would have been that path — and it's now a no-op (see above).
- **Impact**: A user who registers + renders their own already-managed repo on a
  second machine destroys their committed instruction files (recoverable via git,
  but a silent, surprising working-tree wipe). Dry-run is the *only* thing that
  surfaces it.
- **Fixes (pick some)**:
  - `bbox_render scope=project` should **refuse or loudly warn** when it would
    replace a non-trivial existing managed file with a near-empty stub, or when
    there are **zero project-scope entries** for the target. Silent shrink-to-stub
    is the dangerous case.
  - Bootstrap's "already generated, nothing to do" detection should distinguish
    "generated AND the store can reproduce it" from "generated but the local store
    has no backing entries" — and in the latter case offer to import the file's
    content as entries (the thing `bbox_absorb` used to do).
  - Document the second-machine story explicitly: what to do when the repo is
    already managed but the store on this host is empty.

## MEDIUM — render target paths are stale in both the README and the tool's own description

- **README step 5 / config table** say `scope=global` patches
  `~/.claude-shared/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md`.
- **`bbox_render` param help string** (the live schema) says the same:
  "surgically patches each provider's global-memory file
  (~/.claude-shared/CLAUDE.md, ~/.codex/AGENTS.md, ~/.gemini/GEMINI.md)".
- **Actual behavior**: render CREATEs `~/.blackbox/BLACKBOX.md` (the 25KB canonical
  shared doc) and APPENDs a small managed region (an `@.../BLACKBOX.md` pointer) to
  `~/.claude/CLAUDE.md` — **not** `~/.claude-shared/CLAUDE.md`. Gemini got
  `~/.gemini/GEMINI.md`.
- **Impact**: Anyone reading the docs (or the tool description) to predict which
  files get touched is wrong about the Claude target dir and unaware of the new
  `~/.blackbox/BLACKBOX.md` indirection. The `~/.claude-shared` migration note in
  README step 2 compounds the confusion.
- **Fix**: Update README + the `bbox_render` schema doc string to the real targets
  (`~/.blackbox/BLACKBOX.md` + `~/.claude/CLAUDE.md`). Note the BLACKBOX.md
  indirection (provider files only carry an `@import` pointer now).

## MEDIUM — `?surface=ops` is undocumented

- The MCP surface selector is the difference between a usable ops install and
  whatever the default surface exposes, but the README step 3 connect snippets use
  the bare `/mcp` URL with no `surface` query param, and nothing in the README
  explains surfaces, what `ops` includes, or what other surfaces exist.
- `bbox_mcp_surface` exists as a tool but the wiring-time query param isn't
  mentioned where a new user wires their CLIs.
- **Fix**: Document `?surface=ops` (and the available surfaces) in the step-3
  connect block, or state the default and when to override it.

## LOW — README step 3 Claude config path glob is off for this layout

- README: **Claude Code** — `~/.claude*/.claude.json`.
- On this machine the MCP config lives in **`~/.claude.json`** (top-level file).
  The glob `~/.claude*/.claude.json` matches *directories* named `.claude*` with a
  nested `.claude.json` and found nothing here.
- **Impact**: minor; a literal reader looking for `~/.claude/.claude.json` won't
  find it. The real edit target is top-level `~/.claude.json` `mcpServers`.
- **Fix**: clarify the canonical path (`~/.claude.json`) vs alt config dirs.

## LOW — README steps 1–2 are systemd-only; no macOS/launchd path

- Steps 2/2a are pure `systemctl --user`. On darwin there is no systemd; the
  daemon here was already running by some other means (a bare process, PID 1171,
  `~/.local/bin/blackboxd`). No launchd plist / `brew services` / background
  guidance for macOS.
- **Fix**: add a short macOS section (launchd plist or "run it however") so the
  "run as a service" step isn't a dead end on darwin.

## LOW (environment note, not a doc bug) — partial install on the "running" machine

- README step 1 installs `blackboxd`, `blackboxd-dev`, `bro` and copies
  `system-defaults/memories/`. This host had only `blackboxd` installed — no `bro`
  TUI, no `blackboxd-dev`. Worth a "verify your install is complete" checklist
  item, since "it's running" can hide a partial step-1.

## MEDIUM — `cargo test` fails on a fresh machine because `bro-harness` isn't installed (and one panic cascades into 18)

- **Symptom**: `cargo test --lib` on this fresh host fails **18 tests** in
  `orchestration::{allocator,brofile,mcp,providers}`. 17 of them panic at the
  *same* spot — `src/util.rs:18:26`, `TEST_ENV_LOCK.lock().unwrap()` — with
  `PoisonError`.
- **Root cause (1 real failure)**:
  `orchestration::allocator::tests::probe_quota_capacity_participates_in_scoring`
  panics at `allocator.rs:1891`. The test injects probes for GLM (0.95
  utilization) and Claude (0.1) and asserts some candidate has a
  `quota_capacity` score `< 0.1` (the saturated GLM lane). But GLM / DeepSeek /
  Brodex dispatch through **`bro-harness`**, and on a fresh machine that binary
  isn't installed (`which bro-harness` → not found; `BRO_HARNESS_BIN` unset). So
  `provider_binary_missing(Glm)` (`allocator.rs:1052`, via
  `resolve_bin(provider.bin())`) is true, the GLM lane is excluded at
  `allocator.rs:786` **before** any `score_components` are computed, and the
  expected `quota_capacity < 0.1` candidate never exists → assertion fails.
  Note `with_provider_bins` (`allocator.rs:1488`) fakes `CLAUDE_BIN` / `CODEX_BIN`
  / `GEMINI_BIN` / `VIBE_BIN` / `OPENCODE_BIN` / `COPILOT_BIN` = `sh`, but **not**
  a harness bin for the bro-harness providers.
- **Cascade (17 fake failures)**: `test_env_lock()` is a process-wide
  `Mutex` these tests share to serialize env-var mutation, acquired with
  `.lock().unwrap()`. When the root test panics **while holding that lock**, the
  mutex is poisoned, so every later test that calls `test_env_lock()` panics on
  the `.unwrap()` of the poisoned guard — turning 1 real failure into 18 and
  burying the actual cause. Which test is "root" is run-order dependent (any
  harness-provider-dependent test can poison first).
- **Impact**: A fresh-machine developer running the test suite sees 18 red,
  none of which obviously points at "install bro-harness." The README step-1
  install list (`blackboxd`, `blackboxd-dev`, `bro`, `system-defaults/memories/`)
  **does not mention `bro-harness`**, yet it's required both for GLM/DeepSeek/
  Brodex dispatch at runtime and for the test suite to pass.
- **Resolution applied here**: `cargo build --release -p bro-harness` →
  `cp target/release/bro-harness ~/.local/bin/`. `resolve_bin` prepends
  `~/.local/bin` (the `BRO_EXTRA_PATH` default) before its `bash -lc command -v`
  lookup, so it resolves without touching the interactive shell PATH. After
  install: orchestration suite went 501→**519 passed, 0 failed**.
- **Fixes (pick some)**:
  - Add `bro-harness` to the README step-1 install list + the "verify your
    install is complete" checklist. It's a required provider binary, not optional.
  - Harden `test_env_lock()` to recover from poison
    (`.lock().unwrap_or_else(|e| e.into_inner())`) so one panic stops cascading
    and the real failure is the only red.
  - Have `with_provider_bins` also fake a harness bin (set `BRO_HARNESS_BIN=sh`)
    so allocator scoring tests don't depend on a real bro-harness install.

## What worked well (so the fixes don't regress it)

- **Global render coexists cleanly with RTK.** RTK had already written `@RTK.md`
  imports into `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`. The global render
  APPENDed its managed region and left the RTK `@import` lines (outside the
  markers) untouched. The marker-preservation contract held exactly as designed.
- **Dry-run render is the thing that saved us** from the project-scope clobber.
  It's the only safety net for the HIGH trap above — which is also why that trap
  needs an in-tool guard, not just an optional preview.
- **Backups**: global render snapshotted originals to
  `~/.local/state/blackbox/backups/<ts>/` before writing. Good.
